Build a basic minimal Microsoft Graph API tester UI for this repo.

Context:
- The Graph service layer already exists at:
  src/server/services/graph/
- Import public Graph functionality from:
  src/server/services/graph/index.js
  or directly from the service files if needed.
- Existing services include:
  - userService
  - calendarService
  - mailService
  - mailboxSettingsService
  - teamsChatService
  - teamsChannelService
  - peopleService
- Auth helpers exist in graphClient.js.
- Token utilities exist in tokenUtils.js.
- GraphError exists in graphErrors.js.
- Do not expose GRAPH_CLIENT_SECRET or access tokens to the browser.
- Mail.Send is not implemented/granted, so do not add a send-mail feature.

Goal:
Create a minimal internal testing app/page that lets me manually test all available Graph service functions and filtering/query options, then displays results in a user-friendly readable format.

Requirements:

1. Add server-side Express routes
Create a new route module, for example:
  src/server/routes/graphTester.js

Mount it in the existing Express app.

Routes needed:
- GET /graph-tester
  - Serves the tester UI page.
- GET /graph-tester/auth/login
  - Starts delegated Microsoft Graph auth using the existing auth client.
- GET /auth/redirect or reuse the existing redirect route
  - Stores tokenSet in the session.
- POST /api/graph-tester/run
  - Accepts JSON:
    {
      "service": "mail",
      "functionName": "listInboxMessages",
      "args": {...}
    }
  - Validates service/function against an allowlist.
  - Calls the appropriate Graph service function with the server-side access token.
  - Returns normalized JSON:
    {
      "ok": true,
      "service": "...",
      "functionName": "...",
      "input": {...},
      "data": ...,
      "summary": "...",
      "meta": {
        "count": 0,
        "timestamp": "...",
        "durationMs": 0
      }
    }
- GET /api/graph-tester/session
  - Returns whether the user is authenticated and basic token info using tokenUtils, but never returns raw tokens.
- POST /api/graph-tester/logout
  - Clears the Graph token session.

2. Security rules
- Never send accessToken, refreshToken, idToken, clientSecret, or GRAPH_CLIENT_SECRET to the frontend.
- Only expose an allowlisted set of functions.
- Mutating functions must require an explicit confirmation flag from the UI:
  {
    "confirmMutation": true
  }
- For mutation functions, show a warning in the UI.
- Do not implement mail send.
- Wrap all service errors using GraphError handling and return readable errors:
  {
    "ok": false,
    "error": {
      "status": 403,
      "code": "...",
      "message": "...",
      "requestId": "...",
      "hint": "Missing permission or admin consent may be required."
    }
  }

3. UI
Create a minimal, clean UI. No heavy framework unless the repo already uses one. Plain HTML/CSS/JS is fine.

UI layout:
- Header:
  - “Microsoft Graph Tester”
  - Auth status
  - Login button
  - Logout button
- Left panel:
  - Service selector
  - Function selector
- Main panel:
  - Dynamic input form for the selected function
  - Run button
  - Mutation warning/confirmation checkbox when needed
- Results panel:
  - Friendly summary
  - Table/cards for common result shapes
  - Collapsible raw JSON viewer
  - Error box with status/code/message/requestId

6. Friendly output formatting
Implement result renderers:
- Arrays:
  - Show count.
  - Render as table when items are objects.
  - Pick useful columns automatically:
    id, displayName, mail, userPrincipalName, subject, from, receivedDateTime, isRead, start, end, location, topic, chatType
- Objects:
  - Render top-level fields as definition list or cards.
- Mail messages:
  - Show subject, sender, received date, read state, body preview.
- Calendar events:
  - Show subject, start/end, location, organizer.
- Users/people:
  - Show displayName, mail/userPrincipalName, jobTitle, officeLocation.
- Chats/messages:
  - Show topic/chatType, message body preview, createdDateTime/from if available.
- Always include collapsible raw JSON.

7. Developer experience

- Add a README section or comment block explaining:

8. Robustness
- If token is missing, return 401 with a login hint.
- If token is expired, attempt refresh using the saved refresh token if available.
- If refresh fails, clear the token session and ask user to log in again.
- Normalize OData query options:
  - top maps to $top
  - select maps to $select when the service expects select
  - filter maps to $filter when the service expects filter
  - orderby maps to $orderby when the service expects orderby
- Do not pass empty strings as options.
- Parse number fields as numbers.
- Parse booleans as booleans.
- Parse JSON textareas safely.
